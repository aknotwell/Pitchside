# Pitchside — Project Plan

## Context
Hackathon brief: build an AI pipeline that turns **synthetic** football events into explainable match intelligence, following five stages: **ingest → interpret → explain → render → personalize**. Also required: multi-language output, live overlays and recaps, and creating or extending synthetic datasets. No footage is provided, and real footage needs licenses, so all data is generated by us.

Judging is split evenly (20% each) across: **Technological Implementation**, **Agentic Design & Innovation**, **Real-World Impact**, **UX & Presentation**, and **Category Adherence**. Every feature in this plan is there to score on at least one of them (see the scorecard at the end).

**Our angle: one match, many broadcasts.** A team of Azure agents acts as a virtual broadcast crew. It watches a live synthetic match and produces a different broadcast for each viewer:
- **Casual fan:** stakes, emotion, simple stats
- **Analyst:** pressure index, PPDA, pass difficulty, momentum
- **Academy player ("Learn mode"):** coaching cues on decisions, scanning and positioning. This is our differentiator.
- **Scout:** player-focus mode that follows one player all match and produces a scouting report at full time

Each mode can be combined with a **language**, a **favorite club** and a **favorite player**.

Team: 3 people, about 2.5 weeks. Stack: Python 3.11+ (managed with `uv`) + FastAPI, React (Vite, TypeScript), deployed on Azure with `azd`.

## Architecture

```
 "Give me a 2–1 comeback with a red card"
        │
[1] Scenario Agent ──► Synthetic Match Generator (physics + tactics sim, seeded)
        │                 ├──► Blob Storage (datasets)  ──► Fabric Lakehouse (published dataset)
        ▼                 ▼
                    Azure Event Hubs  (live ingest)
                          ▼
[2] Intelligence Engine — deterministic Python (Container Apps)
      state, metrics, patterns, key-moment detection → Cosmos DB
      exposed as the  ►  Pitchside MCP Server  ◄  (stats tools for every agent)
                          ▼
[3–4] Broadcast Crew — Microsoft Agent Framework workflow, agents in Foundry Agent Service
      ┌─ Analyst agent     : finds why a moment matters (calls MCP tools)
      ├─ Producer agent    : decides what goes on air, when, for which audiences
      ├─ Persona writers   : fan / analyst / academy coach / scout, in the viewer's language
      ├─ Fact-checker      : rejects any claim or number not backed by MCP data (reflection loop)
      └─ Recap/Scout agent : half-time & full-time recaps, scouting reports
                          ▼
[5] Timed OverlayCue JSON → Azure Web PubSub → React broadcast UI (Static Web Apps)
      2D pitch · overlay graphics · 4 persona panels · "why?" drill-down · recap screen
```

**Key design rule: numbers come from code, words come from agents.** Agents can only state facts they got from MCP tools, and the fact-checker enforces this. This addresses the main reason LLM sports commentary isn't trusted in production.

### Agentic patterns used (Agentic Design, 20%)
| Pattern | Where |
|---|---|
| **MCP tool use** | Our own **Pitchside MCP Server** exposes engine stats (`get_match_state`, `get_player_stats`, `get_moment_evidence`, `compare_players`). It's consumed by our agents *and* usable from GitHub Copilot or Claude Desktop, so any MCP client can query a live match |
| **Multi-agent orchestration** | Agent Framework workflow: Analyst → Producer → Persona writers (fan-out in parallel) → Fact-checker → publish |
| **Reflection / verification** | Fact-checker sends ungrounded drafts back to the writer with the reason, up to 2 retries, then falls back to a template |
| **Planning / resource allocation** | Producer agent manages a limited "screen-time budget" so viewers aren't spammed, prioritizing moments involving each viewer's favorite club or player |
| **Agent-generated data** | Scenario agent turns a natural-language brief into generator parameters and checks the result matches the request |
| **Memory / personalization** | Per-viewer profile + "what this viewer has already been told" in Cosmos DB, so commentary doesn't repeat itself and builds over the match |
| **Human in the loop** | Studio mode: a producer can approve, edit or kill a cue before it goes to air (a real broadcast workflow) |

## Synthetic data (scored under Technological Implementation and Category Adherence)
Better synthetic data is part of what we're judged on, so the generator is a feature, not just scaffolding.
- **Simulation, not random events:** 22 agents at 10 Hz with formation anchors, team shape, pressing triggers and ball physics. Events *come out of* the tracking data, so passes, speeds and distances are physically consistent
- **Calibrated:** a validation report compares output against typical professional match numbers (passes, shots, pass accuracy, distance covered, sprint counts) and ships with every dataset
- **Controllable:** team tactics (press height, tempo, width), player ratings, and a scenario DSL ("goal at 87' from a set piece", "red card at 60'")
- **Agent-driven:** the Scenario agent creates matches from plain English
- **Seeded and reproducible**, with an open schema close to StatsBomb's, documented in `docs/DATASET.md`
- Output: `meta.json`, `events.jsonl`, `tracking.jsonl` per match

## Data contracts (agree on these on Day 1)
Pydantic schemas in `backend/pitchside/schemas.py`, with TS types generated for the front end.
- `MatchMeta`: teams, lineups (id, name, number, position, ratings), tactics, venue, competition
- `TrackingFrame`: `t`, ball `{x,y,z}`, players `[{id,x,y,speed}]` at 10 fps; pitch is 105×68 m
- `Event`: `id, t, type (pass|shot|tackle|interception|carry|dribble|pressure|foul|possession_change|goal|save|card|sub|period), team, player, start{x,y}, end{x,y}, outcome, extra{}`
- `Moment`: `id, t, type, importance, reasons[], evidence{}, players[]`
- `OverlayCue`: `id, t_in, t_out, slot (lower_third|tag|badge|bar|fullscreen), template, data{}, text{lang: str}, audiences[]`
- `ViewerProfile`: `persona, language, fav_club, fav_player, focus_metric`

`OverlayCue` is the timed, machine-readable output that a broadcast graphics system can render ("synchronized graphical overlays").

## Components and owners

### A. Generator + Scenario agent + data platform: **Person 1**
`backend/pitchside/generator/`, `backend/pitchside/agents/scenario.py`
- Simulation, scenario DSL, validation report, Blob upload, real-time replayer to Event Hubs
- Stretch: Fabric Lakehouse + Real-Time dashboard

### B. Intelligence engine + MCP server: **Person 2**
`backend/pitchside/engine/`, `backend/pitchside/mcp/`
- State, metrics (pass difficulty, xG, ball/shot speed, distance and sprint thresholds, PPDA, pressure index, field tilt), patterns (momentum, control vs chaos, tempo), moment detector with reasons
- Pitchside MCP Server wrapping the engine's read-only queries
- Fully deterministic and unit-tested

### C. Broadcast Crew agents: **Person 3**
`backend/pitchside/agents/`
- Agent Framework workflow; Analyst, Producer, 4 Persona writers, Fact-checker, Recap/Scout
- `PITCHSIDE_LLM=foundry|template` switch; template fallback for timeouts and offline development
- Languages: EN, ES, FR, AR, PT to start (agents write long text in the target language; Translator handles short overlay strings)
- Foundry evaluation suite on a fixed set of moments

### D. Front end, API, infrastructure: **shared, with everyone on it in the final week**
`frontend/`, `backend/pitchside/api/`, `infra/`
- FastAPI + Web PubSub groups (match × persona × language)
- React UI: 2D pitch, overlays timed by `OverlayCue`, profile picker, **4-panel "many broadcasts" view**, **"Why?" button** on any cue that shows the agent's reasoning and MCP evidence, studio approval mode, recap screen
- Accessible (keyboard, contrast, captions) and responsive
- Bicep + `azure.yaml`; `azd up` deploys everything; managed identity + Key Vault; Application Insights

## Engineering practices (quality software development)
- Monorepo, `uv` (Python) and `npm` (front end); `ruff`, `pyright`, `pytest`, ESLint, Vitest
- GitHub Actions: lint → type-check → tests → Foundry evals → `azd deploy`; PRs required with one reviewer

- Every Azure dependency has a local stand-in (files, an in-process queue, template text), so the whole app runs locally with `make demo`

## Real-world impact (20%): the story to tell
- **Problem:** broadcasters produce one feed for millions of very different viewers; graphics and commentary are expensive, manual and usually English-first. Data-heavy coverage loses casual fans, and simple coverage bores analysts
- **Solution:** a production-shaped pipeline (event stream in → timed overlay JSON out) that fits the way broadcast graphics systems already work, personalized per viewer and per market at little extra cost
- **Who benefits:** broadcasters and streamers (more engagement, localization at scale), clubs and academies (Learn mode as a coaching tool), scouts (automatic player reports), fans worldwide (their language, their team)
- **Production-readiness evidence:** latency numbers, cost per match, eval scores, IaC deployment, the fact-checker guardrail

## Verification
- `uv run pytest`: schema round-trips, generator sanity bands, metric unit tests, moment detector on scripted scenarios, MCP tool contract tests
- `make gen SEED=42` produces identical output twice
- `make demo` locally and the deployed URL: the pitch animates, overlays are timed correctly, the 4 panels show *different* content for the same moment, and language switching works
- `PITCHSIDE_LLM=template` runs the whole app with no model
- Foundry evals: groundedness, fluency and persona fit tracked in CI
- Targets: event → on-screen cue < 1 s (template), < 4 s (agents); cost per 90-min match measured and reported
